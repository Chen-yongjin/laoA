# 老牛选股助手 · 改版方案（按用户给定布局重构）

> 定位：**股票助手**，是行情软件的有效补充 —— 不替代券商客户端，只做"看一眼就知道该干什么"。
> 本文件是改版的**唯一对齐依据**：界面做成什么样、旧功能去哪儿、默认值是多少，以这里为准。
> NAS 服务器版（`/vol4/@apphome/dsh/选股/` 根目录）**一个字节不动**，本次只改 `laoA/`。

---

## 一、标题区（不再是"状态栏 + 一排按钮"）

```
老牛选股助手  ·  运行状态：正在下载历史数据 48%（写入行情 62 万行 / 285 万行）   [显示详情] [关于软件]
```

- **软件名称 + 运行状态**在同一行：状态就是"现在在干什么"，下载/刷新/选股/盘中轮询全部显示在这里
  （原来状态、进度条、按钮分散成三行，改成一件事只说一次）。
- **【显示详情】**：点开看完整信息（数据日期、股票数、库大小、下次检查、今日提醒计数、数据目录、日志路径、
  自检阈值）。原来散在状态栏与多处提示里的长期信息都收进这里。
- **【关于软件】**：版本/版权/源码地址/复制版本信息。
- **原则：尽量减少弹窗式提示**。只有"必须让用户做决定"的才弹；
  其余一律写进标题区状态 + 通知消息（通知是否发、发哪些，**全部由用户配置**）。
  **2026-09-17 更新：那时把"输入 Key"那一个弹窗也去掉了**（改成页内提示）；
  **2026-09-18 再更新**：用户澄清"不要配 Key"指的是**程序里不许预置开发者自己的 Key**、
  **不是不给用户填**（原话："设置里让你不要配 KEY，但是你也要给个 key 的输入口啊"），
  所以**同花顺那一行的 Key 输入框又回来了**（页内控件，不是弹窗）。
  全应用仍然只剩**一处**模态确认（覆盖/删除公式，不可撤销的决定）。
- 标题区**不再放操作按钮**：数据下载/刷新/选股都在各自的页面里（数据在「系统设置」，选股在「策略选股」）。

### TAB 2 自选股池
- **添加入口**：代码 + 备注 →【添加自选】（回车即加）。
- **表格列**（当时 **8 列**；**2026-09-21 起 10 列**，加了 `加入日期`、`盈亏`，见 `21·19`）：
  `名称(代码) | 现价 | 涨幅 | 市值 | 换手 | 板块 | 来源 | 监控开关`
  - **现价 / 涨幅**：实时快照（60 秒轮询）优先；没有实时数据时用本地最新收盘价，
    **单元格里不加任何符号**（`*` 已彻底去掉），区别写在 tooltip 里（"这是本地最新收盘价（MM-DD），不是实时价"）；
  - **市值** = **流通市值（亿）**、**换手** = **实时换手率（%）**：都来自实时快照，
    **取不到显示 `—`（不是 0）**——0 亿市值 / 0% 换手是真实存在的值；
  - **板块**：`stock_basic.industry`；
  - **来源**：`策略·<策略名>` / `公式·<公式名>` / `自选` / `策略+自选`（沿用现有 `pool.source_label`）；
  - **监控开关**（2026-09-17 由原来的「提醒」列改名）：文字是 `开启` / `关闭`，
    **点一下这一格就能切换**（与右键【关闭监控】/【打开监控】同一个动作）；
    **今日最新一条提醒的完整内容挪进了这一格的 tooltip**（内容没丢）。
- **交互**（三张表统一）：
  - 悬浮 → 显示备注（有备注的行）；
  - 右键菜单 → 【删除】/【关闭监控】↔【打开监控】；
  - **单击 → 打开雪球个股页**（`https://xueqiu.com/S/SH600000` 这种，复用 `notify/windows.py:to_xueqiu_code()`）。
- 本表**同时**显示策略/公式选出来的票（`来源` 列区分）与手工添加的自选股 —— 这是"池子"的唯一入口。
- 表头右侧一行小字：`共 N 只（策略 M · 自选 K）`。

### TAB 3 持仓监控
- **添加入口**：代码 + 成本价 + 备注 →【添加持仓】；同一行右侧一个复选框 **T策略**（默认关，与「系统设置」里的是同一个开关）。
- **表格列**（**10 列**）：`名称(代码) | 成本价 | 现价 | 涨幅 | 市值 | 换手 | 盈亏比例 | 止损位 | 止盈位 | 监控开关`
  - 盈亏比例 = `(现价 − 成本) / 成本`，涨红跌绿，缺价显示 `—`（不显示 `0.00%`）；
  - 市值/换手 = 与自选股池**同一套口径**（流通市值亿 / 实时换手率%，取不到 `—`）；
  - 止损位/止盈位 = `成本 × (1 ∓ 止损/止盈比例)`，比例在「系统设置 → T策略」里改；
  - 监控开关与自选股池同一口径（`开启`/`关闭` + 点一格切换 + tooltip 里带今日最新一条提醒）。
- 交互同上（悬浮备注 / 右键删除与开关监控 / 单击开雪球）。
- **数量不再出现在界面上**：持仓只记"代码 + 成本 + 备注"（用户给定的字段），
  原来的"数量"字段保留在库里做兼容（详见第五节）。

## 五、数据与存储的兼容

- **持仓"数量"**：界面不再显示、添加表单不再要求；库里 `position.quantity` 保留。
  新加的持仓写入 `quantity = 0`，并把 `load_positions` 的门槛从 `quantity > 0` 改成"未被显式平仓"，
  这样"只记代码+成本+备注"的持仓也能正常出现（老库里的行不受影响）。
- **"现价"口径**：优先用**实时快照**（60 秒轮询，与盘中提醒同一份数据）；
  没有实时数据（收盘后 / 没配 Key）用本地日线最新收盘价 —— **2026-09-17 起单元格里不加任何符号**
  （原来的 `12.34*` 被用户误读成"监控状态标记"），改由 **tooltip** 写明"这是本地最新收盘价（MM-DD），
  不是实时价"。绝不用**后复权价**冒充现价（老代码在持仓页混用过后复权价，这次改掉）。
- **"市值 / 换手"口径**：都取**实时快照**里的 `circ_mktcap`（流通市值，亿）与 `turnover_rate`（%）；
  快照只在交易时段取、且来源得提供这两个字段，**取不到一律 `—`**（绝不拿 0 冒充"没取到"）。
- **自选股上限** `watchlist_max`（20）保留：超出时**明确提示**（不静默丢弃）。

21·6. **公式引擎接入「快照字段」与「离线标记」两类新字段**（2026-09-18，commit `d3660bf`；
     当天又补了 `热门行业` 与 `沪市` / `深市` / `创业板` 三个标记，见 21·7）。

    背景：用户在 2026-09-17 给过一条策略 —— **流通市值 10–300 亿 / 放量 50% / 量比 ≥1.5 /
    换手率 >5% / 价格 3–50 元 / 排除 ST、科创、北交所** —— 当时只解答没落地。这一轮落地成
    5 个可直接在编辑器里写的字段：`流通市值`、`换手率`（快照类）与 `ST`、`科创`、`北交所`（离线标记）。

    **① 为什么"快照字段"与"离线标记"要分开**：两者取数成本完全不同 ——
    `流通市值` / `换手率` **要联网**（日线里没有这两个数，同花顺的快照端点也不返回它们，
    见 `data/sources.py` 的 `SUPPLEMENT_FIELDS`；由 `formulas.snapshot_extra()` 取**一趟**
    实时快照，含"按字段从后面来源补齐"），而 `ST` / `科创` / `北交所` **完全不用联网** ——
    它们由名称与代码直接推出来（`formula.is_st_name` / `is_star_market` / `is_bse`），
    并且在 `Series.__post_init__` 里**自动补齐**，所以运行 / 选股 / 成绩单哪个入口都直接可用。
    分开写还避免了一个误导：让用户以为"用了排除条件就要联网、就没法回测"。

    **② 为什么缺值走 NaN、而不是报错**：快照取不到时（非交易时段、来源都取不到），
    这两个字段铺成**整条 NaN** → **条件不成立**（不产生信号），而**不是**抛错。
    理由是量级：公式要在**全市场几千只票**上逐只求值，一只报一次错会把结论刷成一片错误，
    用户真正需要的信息（"这两个数现在没有"）反而被淹掉；而且在 `preview_hits` /
    `formula_group.run_enabled_formulas` 里各补**一句人话**（`snapshot_extra()` 的 `note`）
    就已经说清了 —— 即 `⚠️ 市值/换手这两个数现在取不到（没有实时行情快照），用到它们的条件一律不成立 —— 所以可能一只都选不出来。交易时段再试，或者在「系统设置 → 数据来源」里确认来源可用。`

    **③ 为什么不设英文别名**（`LTSZ` / `HSL` 故意不登记）：别名会**占住那个名字** ——
    用户再写 `LTSZ:=流通市值`（把它当自己的中间变量）就会被引擎拒绝
    （"变量名与内置字段同名"），而他不写别名时本来是能用的。所以要用的只有**中文名**
    （与既有的 `量比` / `连板` / `涨停天数` 一致），编辑器右侧「变量」面板点一下就插入。

    **④ 为什么只有最后一根 K 线有值**：这两个数是"当下的事实"，历史日线里**根本没有**这个概念。
    所以铺法是"**最后一个位置**是今天、前面全 NaN"，于是 `流通市值>=10` 这种直接比较能用
    （选股本来就看最后一根），而 `MA(流通市值,5)` 这类滚动计算**不会产生信号** ——
    这是**刻意的**：宁可不出信号，也不拿今天的值倒推出一条看起来很合理的假均线。

    **不发请求的保证**：只有公式**真用到**那两个字段时才取那一趟快照
    （判据 `formula.fields & SNAPSHOT_FIELDS`，`formulas.preview_hits` 与
    `strategy/formula_group.run_enabled_formulas` **两处都判**）—— 纯价格/成交量公式
    的开销与加这两个字段之前完全一样。

22. **"免 Key 能用"的边界**（2026-09-18 **第三次改写**）：这条改过三版 ——
    最早写"只有两张表的实时快照免 Key"；2026-09-17 改成"概览/日更/历史都补成免 Key 了"；

    所以现在的事实是：**概览与日更免 Key 能用；历史必须配 Key；选股还没打通**。逐条如下：

    | 能力 | 没 Key | 实现位置 |
    |---|---|---|
    | 概览的「成交与情绪」7 个数 + 宽基 7 只 | ✅ | 没 Key / Key 无效时 `market._public_client()` 换成 `public_market.PublicMarketClient`（**同花顺客户端的替身，同样三个方法**），结果里 `price_source == "public"`；`_collect_overview()` **一行都不分叉**，"谁是主源"只落在 `fetch_overview()` 一处 |
    | 两张表的 `现价/涨幅/市值/换手` | ✅ | `data/sources.py` 的 `_SNAPSHOT_FETCHERS["public"]`（不变） |
    | 日更（当日日线 / 涨停池 / 代码表 / 交易日历） | ✅ | `sync.daily_update()` 拿不到凭据时改派 `public_sync.daily_update_public()` —— **分派只写这一处**，因为日更是"界面按钮 / 定时任务 / 命令行"三个入口共用的 |
    | **历史数据** | ❌ **没有**（只有免 Key 日更"一天天攒"；见"未落地"第 2 条） | 免 Key 那条路没有 dump、没有历史包、也没有逐只补缺口 |
    | 同花顺 10 年 dump、涨停池**明细**、**情绪/板块指数**、**行业归属**、**竞价扫描** | ❌ 仍要 Key | `sync.sync_daily()` / `intraday.py` 构造的是同花顺客户端；`sync.sync_industry()` 走同花顺目录 + 成分股；`.TI` 类代码在免 Key 源归 `unsupported` |

    **三个口径 / 设计决定**（这一轮拍板的，写在这里免得以后被"顺手改回去"；
    另外**来源主次本身也是一条拍板**：`["hithink","public"]`，同花顺主源、公开源兜底，
    理由是公开接口实测限流 —— 腾讯 `fqkline` 700 只左右开始连续失败、新浪列表接口回 456）：

    a. **涨停家数排除 ST 与北交所，是为了对齐同花顺**（`public_market.LIMIT_EXCLUDES_ST` /
       `LIMIT_EXCLUDES_BJ`，不是漏了）。实测 2026-09-17：按"现价 == 涨停价"扫出 **50 只**，
       同花顺涨停池当天 **47 只**，差的 3 只**全是 `*ST`**；再核对库里 1188 个交易日的同花顺涨停池
       —— **`is_st` 全为 0、且不含任何北交所代码**，说明同花顺的口径本来就是"沪深、不含 ST"。
       跟着参照物的口径走，是为了**加不加 Key 不让同一个数字跳 3 只**。
       同一份 `counts()` 里 **涨跌家数口径相反**（含 ST 与北交所）——那是"全市场涨跌"，本来就该含；
       **停牌不计入涨跌**（成交量 0 的票既没涨也没跌，算成平盘会凭空多十几只）。
    b. **免 Key 概览的涨跌停家数是"5 分钟一档"**（`public_market.SCAN_TTL = 300`，
       与 `market._BREADTH_TTL` 同一节拍）。因为免 Key 路径没有现成池子，
       涨停/跌停/炸板与涨跌家数**都是同一趟全市场扫描**（新浪代码表 55 页 + 腾讯快照 56 批 ≈ 111 个请求 / 103 秒）
       算出来的；概览页每 55 秒刷一次，跟着刷就是"每 55 秒重扫全市场"（限流/封 IP）。
       所以【立即刷新】**不穿透**到扫描层（`PublicMarketClient` 故意不接 `force`），
       页脚**逐项**写清"涨跌停家数、涨跌家数每 5 分钟更新"（`market.footer_text()` 按 `pools_slow`
       与 `breadth_enabled` 两个键拼；有 Key 时只有涨跌家数那一项）。
       同一趟缓存还有个副产品：**翻页免费**（`request()` 从缓存里切片，6 页不再发请求）。
    c. **复权怎么算：最终只落地了"用交易所昨收"这一条**（另一条"事件表"路线实现过又被删，见"未落地"第 2 条）。
       **落地的那条**（`public_sync.detect_ex_right()` / `factor_step()`，还在）：日更写"今天"这一根时，
       拿**快照里的昨收**（腾讯 `[4]`，交易所**在除权日调整过**）与库里最后一根的收盘价比 ——
       一致就不动，不一致就是除权，`k = 库里前收 / 快照昨收`，今天的因子 = 上一根的因子 × k。
       不需要任何事件明细，也不用多打接口。
       **被删掉的那条**（决策依据留在这里，避免以后又拍一次板）：公开源不给事件表，
       所以曾想用"复权序列反推"，实测**都否掉了** —— `hfq` 与它自己的不复权序列不自洽
       （000011 在 139 个交易日里 135 天比值乱跳、最大 3.1%）；`qfq` **会漏事件**
       （600017 的 2025-10-31、2026-06-12 两次派息同花顺都记着、它的 qfq 一点没动），
       也会**造假事件**（600007 真事件 1.05928 逐位相同，旁边多 5 个 ±0.4% 噪声阶跃）；
       网易 `chddata` 502、东财 `push2his` 连接被重置、新浪 `klc_kl.js` 是私有压缩格式。
       于是改成取**事件本身**：新浪分红配股页（`vISSUE_ShareBonus`）的
       公告日期/送股/转增/派息/进度/除权除息日，实测与 NAS 库里同花顺 `adjust_event` 抽样
       **8/8 逐字段一致**，因子按 **`sync.adjust_ratio` 那条公式**算（与服务器版同一条）。
       **结论**：这条路线本身是验证过的，但**当前代码里没有它**；如果以后要恢复"免 Key 拿历史"，
       这一节就是现成的实现依据。
    d. **能力声明仍然只写"已经接进链路"的**：`sources.py` 注册表里 `public` 的
       `capabilities` 仍只有 `snapshot`（那是它作为**两张表数据源**的能力），
       这条硬规矩不变；它那条 `note` 现在也把边界写清了：
       **概览有免 Key 兜底（走 `public_market` 的全市场快照），但完整历史下载与选股要 Key**
       （自检要的复权事件/行业归属只有同花顺那条路给得到）。

    **边界与「不在代码里」的东西（写在方案里，别让文档替代码承诺）**：

21·18. **性能：点一下卡一下（机器码每次重算）**（2026-09-21 主人实报："新版程序好像资源占用变高了，
      点策略什么的都会卡一下"）。

      **定位（有测量）**：写了个脚本按"Windows 上三条 PowerShell 各 400ms"模拟硬件指纹开销，修前：

      | 场景 | 修前 | 修后 |
      |---|---|---|
      | `machine_code()` 第 1 次 / 第 2 次 | 1.20s / **1.20s**（没缓存） | 1.20s / 0.000s |
      | 连点 3 次【策略编辑】（走 `status_text`/`is_licensed`） | **3.62s**（每次 1207ms，且每次都读硬件） | **8.1ms**（每次 2.7ms，**硬件查询 0 次**） |
      | 日常路径 9 次调用（启动检查/锁刷新/关于/保存） | 每次 1.2s | **共 0.42s、硬件查询 0 次** |
      | 打开授权对话框那一下 | 同上前提下 1.2s（同步、冻界面） | **1.21s 但在后台线程**（界面先显示"正在读取…"），之后走缓存 4ms |
      | 桌宠空闲 10 秒 | CPU 0.004s、活跃定时器 **0** | 不变（它本来就没问题） |

      结论：锅不在桌宠（它空闲时一个定时器都没跑），而在 `licensing.machine_code()` ——
      **每次调用都重新问硬件**，而 Windows 上是**三条** PowerShell（`_ps` 各起一个进程），
      点【策略编辑】、刷新授权状态、打开「关于」都会走到它。

      **修法**（按主人 2026-09-21 的追加口径"不用每次都读机器码啊，客户要注册的时候再去读"）：
      ① 三条 PowerShell 合成**一条**（一个进程问完三项）；
      ② `license_status()` **默认根本不读机器码** —— 日常那条路（启动、点【策略编辑】、
      刷新设置/关于、保存设置）只读授权文件与试用记账，`registered` 的判断是
      "文件里有没有注册码"，**不校验它属于哪台机器**；返回值里 `machine` 是空串，
      一眼能看出"这份状态没读过机器码"；
      ③ 只有 `verify_machine=True`（**打开授权对话框 / 点【注册】**那一路）才读机器码：

21·29. **`CODELIKE` / `NAMEINCLUDE` + 跨行语句**（2026-09-21 主人贴来一段 5 行的片段）

    主人贴的（原样）：

        BAN := NOT(CODELIKE('300') OR CODELIKE('301')     {创业板}
                OR CODELIKE('688') OR CODELIKE('689')     {科创板}
                OR CODELIKE('43')  OR CODELIKE('83')      {北交所}
                OR CODELIKE('87')  OR CODELIKE('88')
                OR CODELIKE('920'))
           AND NOT(NAMEINCLUDE('ST'));

    **两个函数**（新增，函数总数 73 → 75）：
    - `CODELIKE('前缀')`：代码以该串开头 → 1，否则 0（通达信语义就是前缀匹配）；
    - `NAMEINCLUDE('关键字')`：名称包含该串 → 1，否则 0（比较时两边转大写，`st` 也认）；
    - 两者都是**逐票恒定**的：一条公式跑的是某只票的整段序列，而代码/名称不变，
      所以整列同一个值（用 `np.full` 造常量数组，不是"只给最后一根"）；
    - ⚠️ **`result=_BOOL` 是关键**：它俩要能直接进 `NOT(...)` / `OR` ——
      声明成数值的话逻辑运算会当场报"需要条件"，而主人那段正是 `NOT(CODELIKE(...) OR ...)`。

    **跨行语句这一条：实测已经能跑，不必改断句逻辑** —— 这条要留个记录，
    免得下次又有人"按行分隔语句"这个描述去改一个本来没坏的地方。真实情况是：
    - 词法阶段**不产生换行 token**，所以 `expr()` 本来就会跨行读到括号闭合；
    - `_semicolons_to_newlines()` 已经把引号外的 `;` 归一成换行；
    - 于是"一条语句横跨 5 行 + 中间夹 `{}` 注释"、"括号未闭合续行"、"`;` 一行两条"
      四种写法全都编译通过（本轮补了 4 条用例钉住，含"报错行号仍指向原始行"）。
    **真正让主人那段跑不起来的不是断句，而是它只是一段"只定义变量"的片段** ——
    `BAN := …` 之后没有最后那行条件（通达信里同样不算一条完整选股公式）。
    所以这一轮的第三个改动是**把这条错误说成人话**：
    改成「这条公式只定义了中间变量 BAN，没有写选股条件」+ 提示「在最后再加一行 `BAN`」
    —— 直接给出该补的那一行，他照抄就能跑。

    用例：`tests/test_tdx_compat.py` 第九节 12 条（主人那段补一行后对
    创业板/科创/北交所/ST 的排除结果、跨行编译、片段错误点名变量、`CODELIKE` 10 组前缀、
    `NAMEINCLUDE` 4 组包含、能进 `NOT/OR`、与板块标记等价、四种断句写法、跨行后的行号）。
    文档：`docs/通达信兼容性.md`（函数数 → 75、加这两个、加"排除板块的等价写法"小技巧）。

21·31. **结果表【加入自选】那一格的尺寸：改成"按字体现量"**（2026-09-21 主人："选股结果界面的
     加入自选调整一下大小，框体有点小，字显示不全"）

     **症状**：结果表最后一列的【加入自选】按钮比字窄，四个字被切掉一部分；
     加过之后显示「已在自选」的那一格同理。

     **根因（实测，别凭猜）**：那一格的宽度不是表格按文字算的，而是控件自己的最小尺寸决定的，
     而当时的尺寸只来自 `QPushButton.sizeHint()` —— 这个值是**缓存**的，换字号之后不一定跟着长：
     Linux 实测 12pt（≈ Windows 125% 缩放那一档）时"加入自选"文字宽 **64**、算上按钮自己的
     内边距要 **90**，而 `sizeHint().width()` 还停在 **80**（10.5pt 时的值）→ 两边各切几像素。
     高度同理：15pt 时文字本身就 24 高 + 上下内边距要 32，而按钮还是 30。
     （`sizeHint()` 还有一个更坑的地方：它**不理会** `setMinimumWidth` —— 实测
     `minimumWidth()=88` 时 `sizeHint()` 仍是 74。所以判据必须是"渲染出来的宽度"。）

     **改法**（`ui/formula_page.py`）：
     - 新增 `_result_add_cell_size(holder)`：每次填这一格时**现量** ——
       文字宽度取 `QFontMetrics`（两种文案取较宽的，这样"加入自选 / 已在自选"两态同宽、
       列宽不会跳），两侧留白是 `RESULT_ADD_SIDE_PADDING = 20`、上下 `RESULT_ADD_V_PADDING = 8`；
       按钮自己的内边距/边框交给**控件自己的样式**算（`initStyleOption` + `sizeFromContents`），
       两个下限取大 —— 没有写死任何一个像素宽度。
     - ⚠️ **量的时机**：必须在 `setCellWidget` **之后**量。控件还没父窗口时拿到的是应用默认字体，
       而它真正的字体来自表格；实测先量后放，12pt 下差 16 像素（照样切字）。
     - 只 `setMinimumSize`、不 `setFixedSize`：字号变大时这一格要能自己长。
     - 行高跟着抬（`setRowHeight(index, cell_height + 4)`）：默认行高 30，而 15pt 时按钮要 40。
     - 量完调一次 `resizeColumnToContents(RESULT_ADD_COLUMN)`：这一列的宽度是
       `ResizeToContents` 在**放进去那一刻**算的，而这之后我们才把最小尺寸调大 ——
       不重算的话按钮会比列宽还宽（实测 10.5pt 时列宽 93、按钮 96），右边缘被列边界裁掉。
     - **顺手查了同一张表其它列**（主人要求）：`ResizeToContents` 算出来的列宽与文字
       **几乎没有余量**（实测「市值」列 28 像素顶着 28 像素的表头文字），
       换台机器（Windows 微软雅黑更宽）或 125% 缩放就容易切字。给这一张表加了
       `objectName = resultTable`，主题里**只对它**放宽单元格/表头内边距
       （`QTableWidget#resultTable::item { padding: 2px 8px }`、
       `... QHeaderView::section { padding: 4px 9px }`）—— 多出来的这几像素被
       `ResizeToContents` 吃进列宽，文字两边就真空出来了。**别的表一行都没改**
       （自选股池、持仓、大盘不在那条规则的射程内）。

     **用例**（`tests/test_formula_page.py` 3.9 节 5 条，判据统一是"渲染出来的尺寸"）：
     `test_add_button_width_is_measured_from_the_text_not_written_down`、
     `test_added_label_fits_its_text_too`（两种文案都要放得下）、
     `test_add_button_keeps_fitting_when_the_font_is_bigger`（**回归**：字号 +3pt 后重新填表，
     按钮要跟着长、列宽与行高都要够）、`test_result_table_columns_have_room_for_their_text`
     （同一张表逐列查余量）。已实测：把 `_result_add_cell_size` 换回"读 sizeHint"的旧写法，
     前三条**当场红**（不是只写了个跑得通的用例）。

     **文档**：`README.md`（结果表那一节写明尺寸怎么算的）、`快速验收.md` 与
     `docs/WINDOWS-验收清单.md` 各加一条手测（把系统缩放调到 125% 再看不切字）。

21·32. **从结果页加入自选的票，股池里的「来源」不能再变成「自选」**（2026-09-21 主人实报：

21·34. **构建方式从 PyInstaller 换成 Nuitka 编译**（2026-09-22 主人拍板：「用 Nuitka（或 Cython）
       把程序编译一遍，不再加其它壳」；目标是"源码不能被解包还原"）。

     为什么是 Nuitka 而不是商业壳
     ----------------------------
     PyInstaller 只是把 `.pyc` 打进包里 —— 网上随便一个解包工具几分钟就能还原出源码，
     注册机算法、授权逻辑、商业策略全在里面。Nuitka 把 Python **编译成 C 再编成原生 exe**，
     逆向门槛从"解包"抬到"反编译二进制"；而 VMProtect / Themida / Enigma 这类壳对
     "单机终身授权"这个场景并不划算：它们显著抬高杀软误报率（客户装不上比被破解更麻烦）、
     拖慢启动、而且每次改代码都要重走一遍加壳流程。所以这一轮**只换编译方式、不叠壳**；
     将来真要更进一步，先买代码签名证书压住误报，再谈壳。

     改了什么
     --------
     - `build/nuitka_build.py`：主构建脚本（`--standalone` + `--enable-plugin=pyside6` +
       `--include-data-*` + `--nofollow-import-to` 等；参数集中在 `build_command()` 里，
       与 `laoa_trader.spec` 的 `DATAS`/`EXCLUDES` **逐项对应**，有测试守着不许漂移）。
       构建完把 Nuitka 的 `launcher.dist/` 搬成 **`dist/LaoniuTrader/老牛选股.exe`** ——
       产物名是硬承诺（客户下载说明、CI 检查、Release 附件都按它写）。
     - `build/launcher.py`：Nuitka 的主模块（三行，只转发到 `main()`；不让
       `laoa_trader.__main__` 当主模块是为了避免模块名与包内 `__main__` 重名）。
     - **`src/laoa_trader/runtime.py`（新增，本条的真正关键）**：三种运行形态
       （源码 / PyInstaller / Nuitka）下"随包数据在哪、用户可写目录在哪"以前散在
       `assets.py`、`formulas.py`、`config.py` 里各写一份、且**都只认 PyInstaller 的
       `sys._MEIPASS`**。Nuitka 没有 `_MEIPASS`（数据就放在 exe 同级），照旧代码跑的结果是
       "程序能起来，但图标全没了、随包策略列表是空的、用户配置写到程序目录里" ——
       而且**开发机（源码运行）永远看不到**。现在收成一处：`runtime.bundle_dir()` /
       `exe_dir()` / `is_frozen()` / `describe()`，三个调用方只调用它，
       `tests/test_runtime_paths.py` 用临时目录把三种形态**都模拟一遍**逐条断言
       （Nuitka 那份就是 `exe 同级`，PyInstaller 那份是 `_MEIPASS`）。
     - `--cli --version`（打印版本 + 构建形态 + 引擎函数数）与 `--cli --doctor`
       新增的"运行形态 / 程序位置 / 随包资源 / 资源目录 / 随包策略"五行，并**把自检报告
       落盘**到 `<数据目录>/logs/自检报告.txt`：桌面版没有控制台，这份文件
       既是用户报障时要发给我们的东西，也是 CI 验证编译产物的手段（GUI 子系统的 exe
       重定向 stdout 不可靠，读文件最稳）。
     - CI：主构建换成 `python build/nuitka_build.py`（job 时限 60→150 分钟、构建步 90 分钟 ——
       Nuitka 是"编译"而不是"打包"，在 2 核 runner 上慢得多，超时的症状又是
       "测试全过、包没出来"），新增**冒烟步骤**：把编译出的 exe 真的跑一次 `--cli --doctor`，
       断言报告里形态是 Nuitka、随包策略目录与图标目录都解析得到；手动触发时可选
       `builder=pyinstaller` 走备用路径；构建失败时上传 `nuitka.log`/`pyinstaller.log`。
     - **PyInstaller 那条路完整保留**（`build/laoa_trader.spec` 一个字没删、`build/build.bat`
       里也写了退回命令），文档里写明"默认 Nuitka、备用 PyInstaller"以及两者差异
       （体积、耗时、防逆向强度）。

     已知代价（写进文档，不藏着）
     ----------------------------
     首次构建 20~60 分钟（要下载编译器组件）、产物体积比 PyInstaller 版略大
     （依赖摊在产物目录里、没有 `_internal` 压缩目录）、本机（NAS/Linux）没有 C 编译器
     所以**只能靠 Windows CI 验证**（本地能静态核对的部分由
     `tests/test_nuitka_build.py` 的 8 条用例守：产物名、随包数据逐项对应、
     `--nofollow` 与 spec 的 excludes 一致、搬运与改名逻辑、入口脚本）。

21·36. **公式加"盘中快照"字段（现价 / 现涨幅 / 现量比 / 现换手）**（2026-09-23 用户要求：
      「必须加进去啊」）。

      - **动机**：他写了条"开盘抓涨停策略（超短）"（量比>5、涨幅 1%~5%、换手 3%~8%、
        排除 ST/科创/北交所），但引擎算的是**日线**（最后一根 = 上一个收盘日），
        盘中点【运行】看到的不是当天 9:35 的盘面。
      - **做法**：四个字段与 `流通市值`/`换手率` 走**同一条**快照通道
        （`SNAPSHOT_FIELDS` + `formulas.snapshot_extra()`），映射关系收在
        `SNAPSHOT_FIELD_KEYS` 一张表里（`现价→last_price`、`现涨幅→pct`、
        `现量比→volume_ratio`、`现换手→turnover_rate`）。
      - **快照加了量比**：`sources.QUOTE_FIELDS` 与 `SUPPLEMENT_FIELDS` 都加上
        `volume_ratio`；东方财富那路补请求 `f10`（实测与腾讯 `[49]` 同口径），
        同花顺的快照端点没有这一项，所以靠"字段级补齐"从后面来源拿。
      - **两条硬限制**（tooltip、校验提示、文档三处都写）：非交易时段取不到 →
        条件不成立、一只都不出；快照只有"当下"一个值 → **没有历史、不能回测**。
        所以它替代不了"收盘后跑一遍"，两者是互补的。
      - 用例守着三个最容易悄悄错的地方：`现涨幅` 是**百分数**（`pct=3.2` 配
        `现涨幅>=1 AND 现涨幅<=5`）、取快照的判据是"公式用到的字段"（不用就不发请求）、
        映射表必须覆盖全部 `SNAPSHOT_FIELDS`。

21·37. **K 线口径按时间自动切：开盘时间里一律用实时数据**（2026-09-23 用户要求：
      「在软件内置规则里设定，开盘时间里运行的选股，都是实时的，不是开盘时间，采用 K 线」）。

      上一件（21·36）只解决了"能读到盘中的数"，但用户写的策略算的仍然是**日线**
      （`C` = 上一个收盘价）—— 他要的是**内置规则**：盘中跑选股，用的就应该是当时的盘面，
      不能要求他为"盘中"另写一条策略。

      - **做法**：盘中（交易日 9:30–11:30 / 13:00–15:00）用快照的现价**拼出"今天"这一根
        K 线**接在日线后面（`formula.LiveBar` + `load_series(today=/live_bars=/kline_day=)`），
        于是 `C`、`C/REF(C,1)-1`、`量比()`、`C>MA(C,5)` 全部自动变成盘中口径。
      - **换算只有一个比例**：库里是后复权价、快照是不复权价，所以
        `今日后复权价 = 现价 × 库里最后一根收盘 ÷ 快照昨收`（这个比例同时含了历史因子与
        当天除权步长，推导写在 `formula._live_arrays` 里）。它保证
        `今天的后复权收盘 ÷ 昨天那根 = 现价 ÷ 昨收` = 盘中真实涨幅。
      - **三条判据**（任一条不成立就退回日 K，并在结论里写明是哪一条）：开盘时间、
        今天是交易日（读 `trading_calendar`，周末/节假日不看钟点）、取得到快照、
        库里还没有今天那一根。**口径永远显示**（`formulas.Prepared.caliber` →
        【运行】的提示区、结果页、选股完成的那句结论）。
      - **一处判据、两条路共用**：`formulas.prepare_inputs()` 是唯一实现，
        `preview_hits()`（【运行】）与 `formula_group.run_enabled_formulas()`（建池）都调它 ——
        否则会出现"点【运行】选出 3 只、点【开始选股】选出 1 只"，用户没法解释。
      - **没有开关**（当天先加了又划掉）：我一度加了 `intraday_pick_live` 配置键 + 设置页
        「选股口径」那一组勾选框，主人当场划掉 —— "不需要加开关，按照我说的规则来"。
        所以那条规则是**无条件**的：配置里没有这个键、环境变量没有、界面上没有勾选框；
        硬把属性塞进配置对象也不理（判据只认时间，见
        `tests/test_formula_lib.py::test_no_switch_can_disable_the_intraday_caliber`）。
        想对着历史信号复盘就等收盘后再跑一遍 —— 那一轮本来就是日 K 口径。
      - 保留的是**信息**：每次运行都写明"本次口径 = 盘中实时 / 日 K 线（为什么）"，
        并在取不到快照时退回日 K 且把这件事说出来（主人："那是信息提示不是开关，
        用户要据此判断结果能不能用"）。
      - 不接这一根的三种情形也各有用例：库里已有今天那一根（同一天两根会让 REF/MA 错位）、
        最后一根不是全市场最新行情日的票（停牌/缺天，接出来的涨幅是假的）、缺现价或昨收。
        「成绩单」**永远只用日 K**（拿没收盘的 K 线算胜率是错的）。
